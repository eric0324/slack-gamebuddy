## Context

動機見 proposal.md。規則細節見 `specs/splendor/*`。

### 原版規則查證 (Splendor 基本版，Space Cowboys，2014)

查了 Space Cowboys 規則書的整理 (rulespal.com、dized) 和 Wikipedia：

- **人數** 2～4。
- **籌碼**：5 色寶石各 7 個、黃金 5 個；2 人每色拿掉 3 個 (剩 4)、3 人每色拿掉 2 個 (剩 5)、4 人全用 (7)；黃金不論人數都是 5 個。
- **發展卡**：90 張，一級 40、二級 30、三級 20；每級翻開 4 張，被拿走就從同級牌堆補，牌堆空了就空著。
- **貴族**：10 張，每張 3 分，翻開「人數＋1」張。
- **四種動作 (每回合剛好一個)**：
  1. 拿 3 個不同顏色的寶石各 1 個
  2. 拿 2 個同色寶石，條件是拿之前該色庫存至少 4 個
  3. 保留 1 張卡 (翻開的卡，或任一級牌堆頂不給別人看) 並拿 1 個黃金；黃金沒了仍可保留；手上最多保留 3 張；保留的卡不能丟，只能買走
  4. 買 1 張翻開的卡或自己保留的卡；成本扣掉已買卡的折扣 (每張卡給該色永久 1 個折扣)，黃金可以當任何顏色
- **籌碼上限**：回合結束時手上 (含黃金) 超過 10 個要退回到 10 個，可以退剛拿的。
- **貴族來訪**：回合結束時折扣達到條件就自動來訪，不算動作、不能拒絕；一回合最多 1 位，同時符合多位時由玩家選。
- **結束**：有人達到 15 分時，這一輪打完讓大家回合數相同；分數最高者勝，同分時買的發展卡少的人勝。
- **官方規則沒寫清楚的地方**：庫存不到 3 種顏色時能不能拿少於 3 個 (規則書沒有明文；常見的解讀是可以拿全部有的顏色)；所有人都無事可做時怎麼辦 (原版沒有規定)。

來源：
- 規則：https://rulespal.com/splendor/rulebook 、https://rules.dized.com/splendor/rule/components/cards 、https://en.wikipedia.org/wiki/Splendor_(game)
- 牌表：https://github.com/opethef10/PySplendor (`cards.csv` 含等級、`nobles.json`)、https://github.com/monk-time/splendor-fastest-win (`cards.csv`)。兩個不同專案的牌表 (後者沒有等級欄，用分數和成本對應) 90 張逐張比對完全一致；各級張數 (40／30／20) 和規則書相符，每級每色張數都是 8／6／4。貴族 10 張取自 PySplendor 的 `nobles.json` (只找到這一個機器可讀來源；結構是 5 張「兩色各 4」、5 張「三色各 3」；沒有第二份資料逐張比對，實作前建議再對一次實體牌)。

### 程式架構

- 房間邏輯、`runGame` (`afterChange` 讓 bot 行動)、`shuffle`、`reply`、`startTimer`、`lobbyEvent` 都在 `src/common.ts`，照矮人礦坑和富饒之城的用法。
- 富饒之城和矮人礦坑示範了：頻道回合面板用 `ref` 原地更新、「行動」按鈕開 `audience: 'ephemeral'` 的私人選單並用 `replace: true` 原地換內容、按鈕 value 帶 `seq` 擋過期選單、「棄牌重抽」把多選的選取狀態放在按鈕 value 上 (`redrawToggle:<seq>:<已選清單>`)，不改 state。璀璨寶石整套照抄。
- `src/slack.ts` 的 prompt 只有按鈕 (沒有 select)，`perRow` 控制每列幾顆；Slack 一則訊息最多 50 個 block、每個 actions block 最多 25 顆按鈕、section 文字最多 3000 字元。
- 不需要新的 GameEvent 種類、不需要 modal、不需要改 `src/slack.ts`。

## Goals / Non-Goals

**Goals:**
- 不用打字，所有操作都靠按鈕；多選 (拿 3 色、退籌碼) 用點選後確認
- 頻道訊息以文字為主，寶石和卡片不用 emoji (Slack 有時把 emoji 顯示成 `:gem:` 代碼，使用者也不喜歡用 emoji 代表物品)
- 1 位真人 + bot 可以玩完整局；有人掛機、bot 卡住也一定會結束

**Non-Goals:**
- 不做擴充 (城市、交易站、東方等)
- 不做「付款時自選用黃金」「貴族同時符合時自選」(見 Decisions 4、5)
- 不做遊戲中的打字指令、不做自訂秒數或分數門檻
- 不做產生圖片

## Decisions

1. **檔案拆分**：`src/splendor.ts` (engine，state／action／事件／bot) ＋ `src/splendorCards.ts` (90 張卡、10 張貴族、顏色代號與中文、`need`／`shortfall`／`payment` 純函式、卡片顯示文字)。和 `citadelsCards.ts`、`saboteurCards.ts` 的拆法相同。

2. **顏色代號**：`w` 白、`b` 藍、`g` 綠、`r` 紅、`k` 黑、`o` 黃金。按鈕 value 和 state 用代號，顯示一律用中文單字。成本、籌碼、折扣的文字格式都是「白2 藍1」(只列不為 0 的，依白藍綠紅黑金的順序)，沒有時寫「無」。

3. **卡片位置與顯示**：翻開的卡位置是 `<等級>-<1～4>`；顯示「`1-2 綠 1分｜白4`」。保留卡在私人選單中標示「保留 1～3」。按鈕標籤不超過 75 字元 (Slack 上限)，例如「1-2 綠 1分｜白4 (付 白3 金1)」。不用 code block 對齊卡片 (中文在等寬字型裡寬度不穩)，每張一行即可。

4. **付款自動計算**：先用同色籌碼、不夠的才用黃金。原版允許玩家「有同色也故意用黃金付」，但這樣選單要多一層，而且幾乎不會更好 (保留黃金反而比較有彈性)。替代方案「每種付法列一顆按鈕」按鈕數量會爆，不採用。**需要使用者確認。**

5. **貴族自動選編號最小的**：原版同時符合多位時由玩家選。實際上很少同時符合，選誰只影響剩下的貴族給誰；為了少一層選單和一個計時器，自動選面板上編號最小的。**需要使用者確認。**

6. **庫存不到 3 色時拿少於 3 個**：照常見的解讀，庫存有籌碼的顏色不到 3 種時拿全部有的顏色各 1 個；有 3 種以上時一定要剛好 3 種 (不能故意少拿)。**需要使用者確認。**

7. **多選的選取放在按鈕上** (照富饒之城「棄牌重抽」)：
   - 拿 3 色：`pick3:<seq>:<已選代號>` (例如 `pick3:12:wb`) 每按一次產生新的選單；選滿時出現 `take3:<seq>:<代號>`。
   - 退回：`retPick:<seq>:<6 位數>` (白藍綠紅黑金各退幾個，例如 `retPick:12:200001`)；`retPick:<seq>:000000` 就是「重選」；總數剛好時出現 `return:<seq>:<6 位數>`。
   - 選取不寫進 state，送出確認時 engine 重新檢查合法性 (庫存、持有數、數量)，不合法就回「這個選單已經過期」。

8. **按鈕 value 總表** (kind `splendor`，都帶 `seq` 擋過期)：
   | 步驟 | value | 說明 |
   |---|---|---|
   | 頻道面板 | `turnMenu:<seq>`、`status` | 開行動選單 (退回階段開退回選單)／我的狀態 |
   | 行動選單 | `turnMenu:<seq>:<sub>` | sub 是 `take3`／`take2`／`reserve`／`buy` |
   | 拿 3 色 | `pick3:<seq>:<代號>`、`take3:<seq>:<代號>` | 多選、確認 |
   | 拿 2 同色 | `take2:<seq>:<代號>` | |
   | 保留 | `reserve:<seq>:<位置>` | 位置 `1-2` 或牌堆頂 `deck1`～`deck3` |
   | 買卡 | `buy:<seq>:<位置>` | 位置 `1-2` 或保留卡 `r1`～`r3` |
   | 退回 | `retPick:<seq>:<數量>`、`return:<seq>:<數量>` | 多選、確認 |

   每個子選單附 `turnMenu:<seq>`「↩️ 換一個動作」。按鈕數量：保留最多 12＋3＝15 顆、買卡最多 12＋3＝15 顆、拿 3 色 5＋1、退回 6＋2，`perRow: 4`，都遠低於 Slack 上限。
   - `seq`：每次輪到新玩家 +1；頻道面板 `ref: splendor:<seq>`。回合內的階段用 `step: 'act' | 'return'` 區分，動作按鈕只在 `act` 有效、退回按鈕只在 `return` 有效。

9. **計時**：`TURN_MS = 90_000`，逾時跳過 (不用 bot 策略代打：代打會替真人花掉籌碼或保留卡，結果難預期；跳過最單純，而且不改變任何人的資源)。`RETURN_MS = 30_000`，逾時照固定規則自動退 (多的顏色先退、黃金最後)。退回是在玩家已經做完動作之後，不能用「跳過」處理，所以另外計時。

10. **防卡死** (原版沒有，**需要使用者確認**)：
    - 輪到時四種動作都做不到 → 自動跳過 (例如庫存空、保留滿 3 張、買不起)。
    - `passStreak`：每次跳過 (逾時、自動跳過)+1，任何人做動作歸零；達到玩家人數就直接計分。全真人都離開時也會在一輪後結束，不會讓頻道一直被占住。
    - `MAX_ROUNDS = 50`：第 50 輪結束直接計分。正常一局大約 20～30 輪 (每人 20～30 回合) 就有人到 15 分，只有 bot 一直拿籌碼又退籌碼 (買不起、保留滿) 時才會碰到。

11. **回合面板**：一次輪到一則 (`ref: splendor:<seq>`)，回合內更新同一則；輪到下一位時把舊面板改成一行摘要、拿掉按鈕 (照富饒之城 `board(s, ended)`)，避免舊按鈕被誤按。上一步的公告併在下一位的面板裡 (照矮人礦坑)，只有「達到 15 分」「提前計分」「最終結果」另外發 `announce`。
    面板範例：
    ```
    *💍 璀璨寶石｜第 3 輪｜👉 輪到 @B (90 秒)*
    上一步：@A 買了 1-2 綠 1分 (付 白3 金1)
    庫存：白 2 藍 4 綠 3 紅 4 黑 4 金 4
    貴族：貴族 1：紅4 綠4｜貴族 2：藍3 白3 黑3｜貴族 3：白4 黑4｜貴族 4：紅3 綠3 黑3
    三級 (牌堆 16)
    3-1 白 4分｜黑7
    3-2 藍 3分｜白3 綠3 紅3 黑5
    …
    二級 (牌堆 26)
    …
    一級 (牌堆 0)
    1-1 紅 0分｜白3
    1-2 (空)
    …
    👉 @B 2 分｜籌碼 白1 藍2 (3)｜折扣 綠1 紅1 (2 張)｜保留 1｜貴族 0
    @A 1 分｜籌碼 無 (0)｜折扣 綠1 (1 張)｜保留 0｜貴族 0
    ```

    文字估計最多約 1200 字元，低於 section 的 3000 字元上限。

12. **bot 決策** (細節見 `splendor/bots`)：純規則、不用 rng，方便測試。bot 不做長期規劃 (不追貴族、不卡別人的牌)，只朝「缺口最小」的卡前進。

13. **State (草稿，`src/splendor.ts`)**：
    ```ts
    type Color = 'w' | 'b' | 'g' | 'r' | 'k';
    type Gem = Color | 'o';
    type Gems = Record<Gem, number>;
    interface SPlayer {
      id: string;
      tokens: Gems;
      cards: number[];        // 已買的卡 id
      reserved: number[];     // 保留的卡 id (最多 3)
      nobles: number[];       // 來訪的貴族 id
    }
    interface SState {
      game: 'splendor'; channel: string; host: string;
      phase: 'lobby' | 'play' | 'ended';
      players: SPlayer[];
      bank: Gems;
      decks: [number[], number[], number[]];          // 各級牌堆，[0] 是頂
      table: [(number | null)[], (number | null)[], (number | null)[]]; // 各級 4 個位置
      nobles: (number | null)[]; // 場上的貴族 id，顯示編號是 index + 1 (固定不變)，來訪後改成 null
      first: number;          // 第一位玩家 index
      turn: number;           // 輪到的玩家 index
      round: number;          // 第幾輪 (1 起)
      step: 'act' | 'return';
      seq: number;
      passStreak: number;
      lastRound?: boolean;    // 有人達到 15 分

      winners?: string[]; timerSeq: number; timers: { phase?: number };

    ```

14. **Action**：`new`、`join`、`leave`、`start`、`cancel`、`addBot`、`removeBot`、`rematch`、`status`、`turnMenu { seq, sub? }`、`pick3 { seq, colors }`、`take3 { seq, colors }`、`take2 { seq, color }`、`reserve { seq, slot }`、`buy { seq, slot }`、`retPick { seq, counts }`、`return { seq, counts }`、`timeout { id }`。

## Risks / Trade-offs

- [牌表抄錯一張就影響平衡] → 發展卡牌表來自兩個專案逐張比對一致；`splendorCards.ts` 的測試檢查總數、各級張數、每級每色張數、分數範圍、成本總和
- [自動付款、自動選貴族和原版不同] → 列在回報請使用者確認；兩者都只改選單流程，不影響 state 結構，之後要加回自選只多一層選單
- [防卡死的提前計分不是原版規則] → 只在卡死時觸發；正常對局碰不到；需要使用者確認
- [逾時跳過讓掛機的人吃虧] → 跳過不改變任何資源，最可預期；和矮人礦坑「逾時蓋第一張」一樣是保守做法
- [bot 太弱或在某些盤面一直拿了又退] → 有 50 輪上限保證結束；bot 規則簡單，日後可以換更好的策略而不影響 spec 以外的部分
- [面板文字太長] → 每張卡一行、玩家一行，估計約 1200 字元；測試檢查 4 人局面板文字少於 3000 字元
- [按鈕標籤太長] → 卡片標籤最長約 30 字元，遠低於 75 字元上限
